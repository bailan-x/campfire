## 文档是怎么搭的

### 设计方案：四层结构

1. **决策层**（§1–§2）：要解决什么问题、成功标准、范围与明确不做、硬约束。先定"不做什么"，避免范围失控。
2. **定义层**（§3–§9）：拓扑与选型、FR-01~FR-27 功能需求、关键流程、数据模型、API、信息架构。
3. **落地层**（§10–§13）：部署、排期（M0 spike → MVP）、风险与对策、决策记录（含被否决的方案与原因）。
4. **演进层**（§16–§22）：每版追加一次真机事故复盘，固定五段式：**现象 → 证据 → 机制 → 修复 → 真机数据**。

第 4 层是这套文档最有价值的部分：它记录的不是"我打算怎么做"，而是"哪里想错了、证据是什么、最后怎么好的"。

### 用户手册：任务导向四段式

每个功能按 **前置条件 → 步骤 → 验证 → 回滚** 写，不按代码结构写。读者是服主，不是开发者。

### 踩坑文档：按故障域分类

A 环境网络 / B 脚本落地 / C 游戏本体 / D 模组 / E 面板工程 / F 目录生成 / G AI 协作 / H 洞穴生成 / I 控制台 / J 分片重连 / K 登记行。每条都带**可复现的证据**（命令输出、日志行号、文件行号），不是"我记得好像是"。

## 维护约定

- **结论当天落盘**：排查出根因当天写进对应文档，否则上下文一压缩就丢。
- **改代码同步文档**：改接口 → 开发文档 §4/§5；改操作 → 用户手册；改部署 → 交接说明；新事故 → 设计方案追加一节 + 踩坑表加一条。
- **文档不写真实凭据**：IP、Token、口令、私钥路径一律占位（`203.0.113.10`、`CHANGE_ME_*`、`<SSH_KEY_PATH>`），对照表见 `仓库说明.md`。
- **文档版本跟代码走**：设计方案用 v2.x 标注，用户手册/开发文档标注适用面板版本。
